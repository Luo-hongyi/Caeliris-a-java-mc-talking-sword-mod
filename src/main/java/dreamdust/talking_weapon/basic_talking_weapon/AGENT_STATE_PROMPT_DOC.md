# 剑的灵魂：Agent 状态与提示词合成机制设计文档

本文档详细说明了 `Talking Weapon` 模组中 Agent 的状态数值设计（双轨心理模型），分析各项数值对游戏系统的实际影响，并深入解析提示词（Prompt）动态合成与组装的全流程。

> 当前实现状态说明（`2026-03-16`）：
> 本文档中的状态与提示词拼装原则大体仍成立，但记忆子系统已经进入新一轮重构：`DetailTag` 语义、Persona 匹配与 LTM 召回链已更新，而 LTM 生成闭环仍未完成现代化落地。阅读本文时，应将“长期记忆生成 / 反思”部分视为目标设计与旧版骨架的混合描述，而不是全部已经完成的现状。

---

## 一、 Agent 状态值的作用与系统影响

目前系统将 Agent 的“心智”拆分为两个层次：**高频运行状态 (`AgentState`)** 和 **低频人格画像 (`AgentPersona`)**。这些状态部分由程序接管，部分由大语言模型（LLM）驱动。

### 1. 高频运行状态 (AgentState)
反映武器灵魂当下的即时状态，高频更新。

*   **主导情绪 (PrimaryEmotion)**
    *   **机制**：通过类型枚举 (`HAPPY`, `ANGRY`, `FEARFUL`, `NEUTRAL` 等) 表达感性状态。
    *   **更新频率**：高。由 LLM 在需要展现情感波动的触发事件中动态评估并返回。
    *   **系统影响**：作为核心事实注入 System Prompt 中，决定了 LLM 当前对话生成的语气、用词和情绪显化。
*   **情绪强度 (Emotion Intensity)**
    *   **机制**：范围在 `[0, 100]` 间的整数。
    *   **系统影响**：给主导情绪提供了定量的激烈度指征。未来也可用于系统内拦截判断（设定阈值：当激烈度极高，大于 80 时，强制发起互动事件或拒绝执行辅助法术）。
*   **熟悉度 (Familiarity)**
    *   **机制**：单调递增的整数计数器。
    *   **更新频率**：代码直接控制，每次激发技能或交互时自动 `+1`。
    *   **系统影响**：物理意义上的“磨合时间”。提交给 LLM 借此感知双方的结交“年头”，当数值极高，即便好感度平平也有“老伙计”熟稔感的生成体现。

### 2. 低频人格画像 (AgentPersona)
反映武器灵魂的长期情感偏向与累积经历，主要通过后端的反思任务进行缓慢修正。

*   **好感度 (Favorability)**
    *   **机制**：范围 `[-100, 100]`，表征灵魂从极度厌恶到深情的偏向。
    *   **更新频率**：低频。由独立的后台反思流处理任务依据近期的记忆来做出调高或调低决策。
    *   **系统影响**：决定基础互动阵营（嘲讽对抗、冷淡顺从、热血合作等）。被拼接进入后续所有 Prompt 之中。
*   **性格词条 (Traits)**
    *   **机制**：具有文字描述的集合条目（例：“不喜欢被泡在水里”），每条必须关联一个标签（`FocusTag.ENVIRONMENT` 等）。
    *   **更新频率**：由反思过程增加、修正，或由拥有者在编辑 GUI 单独增加。
    *   **系统影响**：提示词的最优解。**仅**在匹配对应的场景 `FocusTag` 时，该词条才会被提取放入提示词的 System Context 里。做到了长篇幅人设不占用常驻上下文 Token。
*   **玩家画像 (Player Profile)**
    *   **机制**：非定量的独立文本片段，存放基于视角的动态评判（如：“持有者是个莽撞粗心的剑客”）。
    *   **系统影响**：将背景故事直接交给了扮演端，提供了连贯“有记忆厚度”的伪背景设定。

### 3. 注意力权重 (Attention Weights)
*   **机制**：可编辑的浮点系数，关联每个特定的 `FocusTag` (如 `COMBAT`, `STATUS`)。
*   **系统影响**：当周边存在多个事件与物品抓取到的时候，将基础重要度乘以注意力权重。计算后的最高值被选作“当前系统 Focus”，不仅指导游戏行为逻辑，还作为提示词性格词条筛选的一级指标。

## 二、 提示词 (Prompt) 动态合成机制

复杂提示词并未直接硬编码，而是位于 `LLMInteractionTask#buildSystemPrompt` 通过 **片段拼接（Modular Construction）**生成，确切流程分为五段核心组合：

### 1. 结构组装顺位

1.  **身份锚定片段 `[Identity]`**
    位于头部的元老规则配置，确立基础扮演规则和禁止输出的内容边界，是从记忆/设置配置表里读取的基础防崩盘段。
2.  **长期记忆摘要 `[Long-term Memory]`** _(如有)_
    为防脱离上下文，提取总结向的重要过往锚点以无格式列表平铺输入。
    当前实现里，这一层的“召回注入”已经存在，但其上游的新版 LTM 生成闭环仍未完成。
3.  **心智融合层 `[AgentRuntime State]`**
    拼合上述提及数值：
    ```text
    [AgentState] emotion=HAPPY (intensity=20/100), familiarity=10
    [AgentPersona]
    好感度: -5/100
    性格特征: ... (此处依据当前的 FocusTags 动态抽取词条)
    对持有者的看法: 不太让人放心
    ```
4.  **感知与情境上下文 `[Contexts]`**
    分化成多级 Context：
    *   `[Context]` 基本的世界参数（所处维度，所在相对位置）。
    *   `[Extra Context]` 从外部传入的非对象化附加参数。
    *   `[Extra Context]` / `[Supplementary Info]` 现在会常驻注入已命中的登记地点语义，例如 `home: (0, 64, 0) [minecraft:overworld] — 主要居所`。
    *   `[Tagged Context]` 同时仍会保留 `custom_specific:<location_name>` 这类地点索引标签，使其继续参与注意力、Persona、LTM 与 tag relation 的链路；若命中地点，还会在入模前主动查询 `LocationRegistry` 获取详细描述并替代其 ID。
5.  **按需构建输出模式 `[Output Format]`**
    由 `buildOutputFormatInstruction` 控制的 JSON 模式构造器。

### 2. 合成架构的核心优势

*   **动态输出控制 (Schema Polymorphism)**
    大模型需要回复 JSON。触发器本身通过传入特殊的 `output_schema`（基于 `LLMOutputSchema` 集合），控制回复包含的内容。当不需要改变情绪时，JSON schema 则被削去掉 `emotion_update` 字段，不仅降低延迟还能显著节约输出 token 和提升成功率。
*   **Token 最大化隔离节约**
    得益于“根据活跃的 `FocusTag` 拿取对应的 `TraitEntry` 性格”这一机制，Agent 可拥有多达上百个海量的人设或好恶字典。但只要当不处于该标签交互事件内，相关人设就绝对不渲染加入 Prompt，直接实现了海量人设设定与零 Token 闲置的并存。
