# Episode Synthesis Prompt Optimization Plan

截至 `2026-04-04`，`episode_synthesis` reflection task 已经具备可运行的 prompt 主线，并且可以通过
`testdata/reflection_prompt_mock_preview/system_prompt.txt`
直接查看当前 system prompt 的实际展开结果。

但当前 prompt 仍存在一个明确问题：

- 输出结构是对的
- 事实来源是对的
- 但生成出来的 `ltm_text` / `profile_text` 很容易过于客观、机械、偏第三方观察口吻

这与我们要的目标不一致。

`episode_synthesis` 不是在产出一份系统纪要，而是在产出 **Agent 自己的内部认知文本**。

因此，本文件用于冻结后续 prompt 优化的核心方向。它先定义问题与目标，不直接修改代码。

## 1. 当前问题

### 1.1 `ltm_text` 过于像客观总结

当前 `memory_synthesis` module 的指令语义更接近：

- 从材料中选择 segment
- 写一段可提交的总结文本

这会自然推动模型产出：

- 事实归纳句
- 事件摘要句
- 第三人称叙述

而不是：

- 剑自己记住了什么
- 剑为什么觉得这件事值得记住
- 剑以什么立场和口吻记住这件事

结果就是 `ltm_text` 很容易成为“事件报告”，而不是“记忆”。

### 1.2 `profile_text` 过于像中立人物画像

当前 `player_profile_update` module 的语义更接近：

- 基于材料重写一段稳定描述

这会把模型推向：

- 中立归纳
- 旁观式描述
- 尽量客观的玩家特征总结

但 `profile_text` 的真实目标并不是“系统玩家画像”，而是：

- 剑怎么看玩家
- 剑逐渐形成了怎样的主观看法
- 这个看法里带着怎样的偏好、偏见、欣赏或警惕

换句话说，`profile_text` 本质上应是 **Agent perspective 下的印象文本**，而不是中立角色档案。

### 1.3 当前 prompt 把模型放进了“任务执行器”位置

当前外层 prompt 明确强调：

- 你正在执行一个 task
- 你必须完成 modules
- 你必须严格遵守 JSON 协议

这些约束对结构正确性是必要的，但副作用是：

- 模型更容易把自己当成“结构化结果生成器”
- 而不是“剑自己的内部反思者”

因此即使 prompt 中已经给了 identity / personality / persona / material，
模型仍可能优先选择安全的“客观总结口吻”。

### 1.4 不能用“强行第一人称”粗暴修复

这里要明确一条边界：

- 玩家经历的物理行为，仍然是玩家在经历
- 剑不能把这些事实错写成“我挖矿了”“我进入洞穴了”

所以问题的修复方向不是“全部改成第一人称”，而是：

- 让文本拥有 **剑自己的主观框架**
- 同时仍然保持 **主体区分正确**

我们真正要的不是单纯的文法变化，而是 **认知所有权**。

## 2. 冻结的目标语义

### 2.1 `ltm_text`

`ltm_text` 的正式目标语义固定为：

- 这是剑自己的长期记忆文本
- 它不是客观纪要
- 它不是系统日志摘要
- 它不是旁观者报告

它应表达的是：

- 剑记住了什么
- 剑为什么记住这件事
- 这件事在剑心里留下了怎样的印象

允许：

- 明显的主观性
- 个性化口吻
- 有取舍的记忆压缩

不要求：

- 面面俱到
- 绝对客观
- 像百科条目一样稳定中性

### 2.2 `profile_text`

`profile_text` 的正式目标语义固定为：

- 这是剑对玩家的低频印象
- 它不是中立角色档案
- 它不是系统生成的人设标签页

它应表达的是：

- 剑越来越觉得玩家是怎样的人
- 剑从哪些行为中形成了这种印象
- 这种印象里包含怎样的欣赏、保留、偏见或期待

因此：

- `profile_text` 可以带明显立场
- 但不能脱离 material 胡乱脑补

### 2.3 `recap_text`

`recap_text` 的目标语义相对更克制：

- 它仍然是剑自己的内部前情提要
- 但它主要承担“阶段性连续性摘要”职责

所以它应该：

- 比 `ltm_text` 更稳
- 比 `profile_text` 更少判断色彩
- 但仍然不应退化成系统播报或开发日志

### 2.4 `favorability_update` / `emotion_update`

这两个 module 暂时不强行追求文学化或强人格化。

它们当前更接近：

- 低频内部状态更新
- 带理由的结构化判断

现阶段允许它们继续保持较强分析口吻。

## 3. 后续优化必须遵守的原则

### 3.1 文本归属必须清楚

后续 prompt 中必须明确说明：

- `ltm_text` / `profile_text` / `recap_text` 都属于剑自己的内部认知文本
- 它们不是系统总结，也不是第三方观察报告

### 3.2 主观性必须建立在事实之上

后续 prompt 不能把“主观”误导成“自由发挥”。

固定原则：

- 可以有态度
- 可以有偏好
- 可以有取舍
- 但所有关键判断都必须能回溯到 material / state / persona

### 3.3 主体区分必须正确

这是后续所有 prompt 优化中最重要的安全边界之一。

必须同时成立：

- 剑可以说“我记得”“我开始觉得”“我不喜欢她那样冒进”
- 但不能把玩家行为错写成剑自己的物理经历

也就是说：

- 可以主观
- 不能主体错位

### 3.4 `ltm_text` 与 `profile_text` 应允许人格化表达

后续 prompt 应明确允许：

- 带有 personality 的措辞
- 带有 stance 的判断
- 带有长期偏好的过滤

否则模型会默认回到更安全的“客观总结体”。

### 3.5 不要求统一成强第一人称

我们不强制所有输出都使用“我”。

真正要求的是：

- 文本必须体现剑自己的视角
- 文本不能退回纯旁观者口吻

是否显式使用第一人称，只是实现方式，不是最终目标本身。

## 4. 明确的反例

后续 prompt 中应明确禁止模型产出以下类型的文本。

### 4.1 客观纪要体

例如：

- 玩家进入洞穴后先采矿后战斗，表现出谨慎探索倾向。

问题：

- 太像系统分析
- 没有剑自己的态度和语气

### 4.2 角色档案体

例如：

- 玩家是一名在地下探索时偏谨慎、倾向先处理威胁再收集资源的人。

问题：

- 像中立人物画像
- 不像剑对玩家形成的印象

### 4.3 主体错位的第一人称

例如：

- 我进入洞穴后先挖了矿，再处理骷髅。

问题：

- 把玩家行为错写成了剑自己的物理经历

## 5. 目标风格示例

这里不作为最终 prompt 文案，只作为方向样例。

### 5.1 `ltm_text` 目标方向

不理想：

- 她在洞口先处理威胁，再进行采矿，说明她在危险环境中保持了克制。

更接近目标：

- 我记得她站在那种狭窄洞口时，先压住了采矿的冲动，宁可把骷髅处理掉，也不肯把自己交给一支冷箭。那一刻我更愿意相信，她不是会被眼前矿石轻易勾走判断的人。

### 5.2 `profile_text` 目标方向

不理想：

- 玩家在探索时通常较为谨慎，会优先处理威胁，再考虑资源获取。

更接近目标：

- 她让我越来越难把“冒险者”简单理解成鲁莽的人。哪怕手边就有矿，她也会先把真正的威胁压下去，再回来拿她想要的东西。我欣赏这种克制，它至少说明她不是把自己性命当筹码的人。

### 5.3 `recap_text` 目标方向

目标上应比前两者更收束，例如：

- 这段时间里，她一直在往地下更深处推进。比起盲目搜刮，我看到的是一种先确认风险、再决定是否继续深入的节奏，而她也开始更频繁地把路线和危险交给我来判断。

## 6. 后续 prompt 修改的推荐顺序

当前不直接改代码，但后续若开始落 prompt，应按下面顺序推进。

### 6.1 先改全局规则

先在外层 task prompt 中新增统一规则：

- 哪些字段是“剑自己的内部文本”
- 哪些字段允许强主观
- 哪些字段仍偏结构化判断

### 6.2 再改单 module instruction

优先改：

- `memory_synthesis`
- `player_profile_update`
- `recap_update`

因为这三个字段最直接影响文本风格。

### 6.3 最后再补反例与负面约束

例如明确禁止：

- 客观纪要体
- 人物档案体
- 主体错位第一人称

## 7. 当前不做的事情

本轮先不做以下改动：

- 不直接修改 `EpisodeSynthesisReflectionTask` prompt header
- 不直接修改各 module instruction
- 不调整 JSON output contract
- 不动 validator
- 不把 `focus_tag_description` 接入 reflection prompt

这些改动都应在后续实现轮中按本文件统一推进。
